SECTION 01

04장 실습 범위와 하드웨어 구조

이번 장은 이미 구성한 MicroBlaze V + 16 KiB Local BRAM을 그대로 사용한다. CPU가 메모리 주소를 생성하고, 해당 위치에 값을 쓰고 다시 읽는 과정을 Vitis Debugger(디버거)에서 확인한다.

구분이번 장의 실제 범위
Instruction 경로ILMB → Local BRAM
Data 경로DLMB → Local BRAM
검증 대상bram_word[4] 배열의 주소와 값
미구현M_AXI_DP의 AXI 주변장치 연결
04장에는 AXI GPIO·UART·Timer를 추가하지 않는다. AXI 구조는 05장, 실제 AXI GPIO 제어는 06장에서 다룬다.
SECTION 02

Vivado에서 BRAM 주소 확인

  1. 기존 Vivado 프로젝트 열기

    ~/soc/hw/soc01_microblaze_bram/soc01_microblaze_bram.xpr을 연다.

  2. Block Design 열기

    soc01_mb_bram을 열고 상단 Address Editor 탭을 선택한다.

  3. ILMB와 DLMB 주소 확인

    두 SLMB 경로의 Base가 0x00000000, Range가 16K, High가 0x00003FFF인지 확인한다.

  4. 미연결 경로 구분

    Incomplete Paths (1)의 /microblaze_riscv_0/M_AXI_DP는 이번 장에서 미사용하는 경로이므로 별도로 주소를 할당하지 않는다.

실제 Address Editor 항목확인값
/microblaze_riscv_0_local_memory/ilmb_bram_if_cntlr/SLMBBase 0x00000000 · Range 16K · High 0x00003FFF
/microblaze_riscv_0_local_memory/dlmb_bram_if_cntlr/SLMBBase 0x00000000 · Range 16K · High 0x00003FFF
Assigned / Unassigned2 / 0
Incomplete Paths1 — M_AXI_DP 미연결
Instruction과 Data가 동일한 물리 BRAM을 보는 구성에서는 두 주소 범위가 같아도 오류가 아니다. 실습에서 정상 검증된 설계를 임의로 바꾸지 않는다.
실제 확인값과 계산값 구분: Base 0x00000000, High 0x00003FFF는 Vivado Address Editor에서 확인했다. 아래 표에 등장하는 0x00001460은 Vitis Watch에서 확인한 bram_word[0]의 실행 주소이다. 두 주소는 서로 다른 개념이다.
SECTION 03

Base · Range · High 주소 계산

주소 범위는 Base Address(시작 주소), Range(크기), High Address(마지막 주소)로 계산한다.

Base : 0x00000000 Range : 0x00004000 = 16 × 1024 byte = 16 KiB High : Base + Range - 1 → 0x00003FFF

32비트 주소로 표현할 수 있는 전체 이론적 범위는 0x00000000 ~ 0xFFFFFFFF(4 GiB)이다. 이 실습에서 실제로 연결된 메모리 영역은 그중 16 KiB뿐이다.

SECTION 06

main.c 원본 코드 입력

저장소의 code/soc04/main.c와 내용이 동일한 원본 코드다. 검증된 변수명과 실행 순서를 변경하지 않는다. 절대 메모리 주소를 하드코딩하지 않고 Linker가 배열 주소를 배치하도록 한다.

#include <stdint.h>
#include <stddef.h>

/*
 * SoC 04 교육용 Memory Map / BRAM 주소 확인 코드
 * 특정 BRAM 절대주소를 임의로 고정하지 않는다.
 */

volatile uint32_t bram_word[4] = {0, 0, 0, 0};

volatile uintptr_t addr_0 = 0;
volatile uintptr_t addr_1 = 0;
volatile uintptr_t addr_2 = 0;
volatile uintptr_t addr_3 = 0;

volatile uint32_t read_0 = 0;
volatile uint32_t read_1 = 0;
volatile uint32_t read_2 = 0;
volatile uint32_t read_3 = 0;

volatile uint32_t stage = 0;

int main(void)
{
    addr_0 = (uintptr_t)&bram_word[0];
    addr_1 = (uintptr_t)&bram_word[1];
    addr_2 = (uintptr_t)&bram_word[2];
    addr_3 = (uintptr_t)&bram_word[3];
    stage = 1;

    bram_word[0] = 0x11111111U;
    bram_word[1] = 0x22222222U;
    bram_word[2] = 0x33333333U;
    bram_word[3] = 0x44444444U;
    stage = 2;

    read_0 = bram_word[0];
    read_1 = bram_word[1];
    read_2 = bram_word[2];
    read_3 = bram_word[3];
    stage = 3;

    bram_word[1] = 0xA5A5A5A5U;
    stage = 4;

    read_1 = bram_word[1];
    stage = 5;

    while (1) {
    }

    return 0;
}
volatile(볼러타일, 최적화 시에도 관찰 가능한 메모리 접근 지정)은 배열과 검증 변수의 실제 접근을 유지하도록 돕는다. uintptr_t는 포인터 주소를 보관할 수 있는 정수형이다. 각 uint32_t 요소는 4바이트를 차지한다.
SECTION 07

Linker Script의 BRAM 배치

  1. Linker Script 열기

    Application의 lscript.ld를 열어 Memory Regions를 확인한다.

  2. BRAM 영역 확인

    lmb_bram_0의 Base가 0x00000000, Size가 0x00004000인지 확인한다.

  3. Stack과 Heap 확인

    Stack 0x400(1 KiB), Heap 0x800(2 KiB) 설정을 확인한다.

  4. Section 배치 확인

    .text, .data, .bss 등 프로그램 섹션이 Local BRAM에 배치되도록 설정되어 있는지 확인한다.

설정 항목실제 실습값

Stack0x400
Heap0x800
배열의 세부 주소는 Linker 배치 결과에 따라 결정되므로 0x00001460을 소스 코드에 고정하지 않는다. 실제 위치는 Debugger WATCH에서 확인한다.

SECTION 09

launch.json 확인 및 Debug 진입

  1. 04장 Launch 설정 열기

    Vitis 중앙 편집 영역의 상단 launch.json 탭을 직접 클릭하여 연다. 왼쪽 목록에서 단순히 다른 항목을 선택하라는 뜻이 아니다.

  2. Launch 설정 확인

    Launch Config Name soc04_memory_map_app_hw_1, Target Connection Local [default], Target Setup Mode Baremetal Debug를 확인한다.

  3. Bitstream과 ELF 경로 확인

    Bitstream은 ${workspaceFolder}/soc04_memory_map/_ide/bitstream/soc01_mb_bram_wrapper.bit, Application은 ${workspaceFolder}/soc04_memory_map/build/soc04_memory_map.elf를 사용한다.

  4. Reset / Program 설정

    Reset Entire System, Program Device, microblaze_riscv_0의 Reset Processor가 선택된 상태를 확인한다.

  5. Debug 실행

    main()에 Breakpoint를 설정한 다음 Debug를 실행하고 RISC-V → Hart #0 PAUSED ON BREAKPOINT 상태를 확인한다.

실제 환경에서 launch.json 탭을 연 뒤 Debug하면 진입에 성공했다. 탭을 열지 않았을 때 발생한 오류의 근본 원인은 확인되지 않았으므로 원인을 특정하지 않는다. 해당 절차는 확인된 우회 순서다.
SECTION 10

WATCH 중간 검증 — stage 2

WATCH(워치, 변수 관찰)에 먼저 stage, addr_0, bram_word, read_1 네 항목만 추가한다. bram_word 옆 펼침 버튼을 누르면 네 배열 요소를 한 번에 확인할 수 있다.

  1. 기존 03장 변수 정리

    WATCH에 남아 있는 memory_data, read_value_1 등 03장 변수는 04장 코드에 없으므로 N/A가 표시될 수 있다. 제거하고 04장 변수를 등록한다.

  2. 실행하여 중간값 확인

    F10(Step Over) 또는 Continue와 Breakpoint를 사용해 stage가 2인 시점을 확인한다.

  3. 읽기 결과 확인

    read_1이 0x22222222가 되고 배열의 네 요소가 초기 기록값인지 확인한다.

WATCH 변수실제로 확인한 중간값
stage0x00000002
addr_00x00001460
bram_word[0]0x11111111
bram_word[1]0x22222222
bram_word[2]0x33333333
bram_word[3]0x44444444
read_10x22222222
실습 스크린샷에서는 main.c 34행에서 일시 정지했다. stage = 3; 문장이 실행되기 전이므로 stage가 2인 것은 정상이다.
SECTION 11

WATCH 최종 검증 — stage 5

bram_word[1]에 0xA5A5A5A5를 다시 기록한 뒤 같은 위치에서 재읽기하여 값이 바뀌었는지 확인한다. 실행을 while (1) {} 위치까지 진행하면 stage가 5가 된다.

WATCH 최종 결과: stage=5, read_1=0xA5A5A5A5, bram_word[1]=0xA5A5A5A5를 확인했습니다. 아래 값은 실제 BRAM 데이터 접근의 Debug 결과이며 AXI 주변장치 MMIO 접근 검증과는 구분합니다.
WATCH 변수최종 검증값판정

addr_00x00001460BRAM 내부 주소
bram_word[0]0x11111111유지
bram_word[1]0xA5A5A5A5재기록 성공
bram_word[2]0x33333333유지

검증 결과: PASS — bram_word[1]에 0xA5A5A5A5를 다시 쓴 후 read_1로 재읽었을 때 동일한 값이 나왔다. CPU → DLMB → Local BRAM 접근 성공이며 AXI 주변장치 MMIO는 이 결과로 검증되지 않는다.
실제 성공 화면에서 main.c 44행의 무한 루프 위치와 stage = 5가 확인되었다. 이는 실제 FPGA 다운로드 및 실행 결과이며, AXI 주변장치 검증 결과는 아니다.

SECTION 14

오류 점검

증상확인 및 조치
Address Editor에 M_AXI_DP Incomplete Paths (1)이번 장에서 미연결인 경로로, BRAM 검증을 막는 오류로 판정하지 않는다.
Build 실패soc04_memory_map/src/main.c의 입력과 lscript.ld의 lmb_bram_0 16 KiB 설정을 확인한다.
Debug 진입 실패 또는 설정 오류중앙 상단 launch.json 탭을 클릭해 열고 Bitstream·ELF 경로와 Program/Reset 설정을 확인한 뒤 재시도한다.
WATCH의 03장 변수에 N/A 표시memory_data 등 이전 Application 변수명을 제거하고 04장 변수명을 추가한다.
stage가 예상보다 작음Breakpoint가 대입문 실행 이전에 멈춘 것인지 확인한다. 최종값은 while(1) 위치에서 확인한다.
배열 주소가 0x1460과 다름주소는 Linker가 결정한다. 실제 WATCH의 주소가 BRAM 범위 내이고 데이터가 올바르면 무조건 오류로 보지 않는다.
