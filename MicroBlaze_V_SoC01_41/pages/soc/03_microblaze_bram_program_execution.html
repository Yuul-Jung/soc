SECTION 01

Reset 이후 프로그램 실행

SoC 02에서 mb_reset이 해제되면 MicroBlaze V는 프로그램 실행을 시작한다. CPU는 임의의 C 함수부터 실행하는 것이 아니라 먼저 Reset Vector 주소에서 명령어 Fetch를 시작한다.

Clock 안정 → Reset 해제 → PC ← Reset Vector → Instruction Fetch → Startup Code → main()
Processor System Reset │ │ mb_reset 해제 ▼ MicroBlaze V │ │ PC = Reset Vector ▼ ILMB │ ▼ BRAM │ │ Reset Vector Instruction ▼ Decode / Execute
SECTION 02

Reset Vector와 PC

MicroBlaze V는 Reset 또는 Debug Reset이 발생하면 Pipeline을 비우고 C_BASE_VECTORS + 0x0에서 즉시 명령어 Fetch를 시작한다. 기본 C_BASE_VECTORS 값은 0x00000000이다.

항목기본 기준의미
C_BASE_VECTORS0x00000000Reset 기준 주소
Reset VectorC_BASE_VECTORS + 0x0Reset 해제 후 첫 Fetch 위치
PCReset Vector를 가리킴다음 실행 명령어의 주소
Reset 해제 직후 PC │ └──▶ 0x00000000 │ └──▶ .text.init │ └──▶ Startup Code │ └──▶ main()
Vector Base Address를 변경하지 않은 교육용 기본 구성에서는 Local BRAM이 0x00000000을 포함해야 한다.

SECTION 04

BRAM 주소 범위

SoC 01에서 Local Memory를 16 KB로 설정하고 Base Address가 0x00000000이라면 교육용 기준 주소 범위는 다음과 같이 계산할 수 있다.

16 KB = 16 × 1024 Byte = 16384 Byte = 0x4000 Byte Base Address = 0x00000000 High Address = 0x00000000 + 0x4000 - 1 = 0x00003FFF
항목교육용 기준값
Local Memory Size16 KB
Base Address0x00000000
High Address0x00003FFF
실제 주소는 반드시 Vivado Address Editor와 Vitis Linker Script에서 확인한다. 이 장의 0x00000000 ~ 0x00003FFF는 SoC 01의 16 KB Local Memory를 Base 0으로 배치한 기준 구성이다.
SECTION 05

SECTION 06

Linker Script와 Memory Section

MicroBlaze V의 시작 코드는 생성된 RISC-V BSP와 Linker Script를 사용한다. .text.init의 _boot에서 트랩 벡터·레지스터·스택을 준비한 뒤 C 런타임과 main()으로 연결된다. 설치된 BSP의 실제 시작 심볼과 섹션 배치를 확인한다.

영역내용확인
.text.init / .text시작 코드와 프로그램 명령어Reset 주소에서 실행 가능한 코드 배치
.rodata / .srodata읽기 전용 상수실제 Linker Map의 섹션
.data / .sdata초기값을 갖는 전역·정적 변수초기화 이미지·실행 주소
.bss / .sbss초기화되지 않은 전역·정적 변수C 시작 과정의 0 초기화
Stack / Heap함수 호출·동적 메모리16 KiB BRAM 범위·영역 중복 없음

큰 라이브러리 호출을 추가하기 전에 코드·데이터·스택·힙의 전체 크기를 확인한다. 이 예제는 UART 출력 없이 메모리 변수로 실행을 확인한다.

SECTION 11

BRAM Read / Write 검증 프로그램

실습 소스: main.c 다운로드. 이 파일 하나를 Application의 main 소스로 사용한다.

UART나 GPIO 없이 같은 BRAM 변수에 값을 쓰고, 다시 읽고, 값을 변경해서 다시 쓰고, 변경된 값을 다시 읽는 과정을 Debugger에서 직접 확인한다. 이 코드는 SoC 03의 메모리 동작 확인을 위해 작성한 교육용 예제이다.

#include <stdint.h>

volatile uint32_t memory_data  = 0;
volatile uint32_t read_value_1 = 0;
volatile uint32_t read_value_2 = 0;
volatile uint32_t read_value_3 = 0;
volatile uint32_t stage        = 0;

int main(void)
{
    // 1단계: 첫 번째 값을 BRAM에 쓴다.
    memory_data = 0x11111111U;
    stage = 1;

    // 2단계: 방금 쓴 값을 다시 읽는다.
    read_value_1 = memory_data;
    stage = 2;

    // 3단계: 같은 BRAM 변수에 다른 값을 다시 쓴다.
    memory_data = 0x22222222U;
    stage = 3;

    // 4단계: 변경된 값을 다시 읽는다.
    read_value_2 = memory_data;
    stage = 4;

    // 5단계: 두 읽기 값을 더한 결과를 다시 쓴다.
    memory_data = read_value_1 + read_value_2;
    stage = 5;

    // 6단계: 최종 값을 다시 읽는다.
    read_value_3 = memory_data;
    stage = 6;

    while (1) {
        // Debugger에서 값을 확인하기 위한 정지 상태
    }

    return 0;
}
단계동작memory_data읽기 결과
초기초기화0x00000000-
1첫 번째 Write0x11111111-
2첫 번째 Read0x11111111read_value_1 = 0x11111111
3같은 위치에 다시 Write0x22222222-
4변경값 Read0x22222222read_value_2 = 0x22222222
5읽은 두 값의 합을 Write0x33333333-
6최종값 Read0x33333333read_value_3 = 0x33333333
① WRITE CPU ──DLMB──▶ BRAM memory_data ← 0x11111111 ② READ CPU ◀─DLMB── BRAM read_value_1 ← memory_data = 0x11111111 ③ RE-WRITE CPU ──DLMB──▶ BRAM memory_data ← 0x22222222 ④ RE-READ CPU ◀─DLMB── BRAM read_value_2 ← memory_data = 0x22222222 ⑤ CALCULATE + WRITE 0x11111111 + 0x22222222 ↓ 0x33333333 ↓ CPU ──DLMB──▶ BRAM memory_data ← 0x33333333 ⑥ FINAL READ CPU ◀─DLMB── BRAM read_value_3 ← 0x33333333
volatile을 사용하여 Compiler가 이 메모리 접근을 불필요한 연산으로 제거하지 않도록 한다. 변수의 실제 BRAM 주소는 Linker가 결정하므로 특정 BRAM 주소를 코드에 임의로 고정하지 않는다.
SECTION 12

Build와 ELF 생성

Application을 Build하면 MicroBlaze V GNU Toolchain이 C Source를 Compile·Assemble·Link하고 ELF 실행 파일을 만든다.

main.c → riscv64-unknown-elf-gcc → Object → Linker Script → soc03_bram_run.elf
확인 파일의미
*.elfMicroBlaze V 실행 파일
Linker ScriptSection → Memory 배치 규칙
Build LogCompiler/Linker Error, Memory Overflow 확인
16 KB BRAM 범위를 넘어가면 Link 단계에서 Memory Region Overflow가 발생할 수 있다. 이 경우 단순히 BRAM 크기를 키우기 전에 어떤 Section이 커졌는지부터 확인한다.

MicroBlaze V용 RISC-V 컴파일러와 생성 BSP를 사용한다. ELF의 Machine은 RISC-V, ABI는 ILP32이며 ISA 옵션은 CPU에서 활성화한 명령어 확장과 맞아야 한다. 이 교재의 기본 구성은 RV32IM / ILP32이다. 캐시는 ISA 옵션과 별도로 하드웨어 설정에서 확인한다. Build Log의 실제 컴파일러 경로·옵션과 Linker Map을 확인한다.

SECTION 17

Debugger로 Read / Write 확인

줄 단위 관찰은 디버그 정보가 포함된 최적화 없음 빌드(-g -O0)로 진행한다. while (1)은 CPU가 반복 명령을 실행하는 대기 루프이며 디버거의 정지 상태가 아니다. 최종값은 Suspend / Halt로 CPU를 멈춘 뒤 Watch에서 확인한다. 각 stage 대입문까지 실행한 다음 아래 표와 비교한다. UG1400 · Debug / Optimization 설정.

Vitis Debugger의 Watch 창에는 memory_data, read_value_1, read_value_2, read_value_3, stage를 등록한다. 각 대입문에 Breakpoint를 걸거나 Step Over로 한 줄씩 실행하면 값의 변화를 직접 확인할 수 있다.

  1. main() Breakpoint

    main() 첫 줄에서 멈춘 뒤 Watch 창에 다섯 변수를 등록한다.

  2. 첫 번째 Write

    memory_data = 0x11111111U; 실행 후 memory_data가 바뀌는지 확인한다.

  3. 첫 번째 Read

    read_value_1 = memory_data; 실행 후 두 값이 모두 0x11111111인지 확인한다.

  4. 덮어쓰기

    memory_data = 0x22222222U; 실행 후 같은 변수 값이 변경되는지 확인한다.

  5. 변경값 Read

    read_value_2가 0x22222222가 되는지 확인한다.

  6. 계산 후 다시 Write

    read_value_1 + read_value_2의 결과인 0x33333333이 memory_data에 저장되는지 확인한다.

  7. 최종 Read

    read_value_3가 0x33333333인지 확인한다.

최종 확인값: stage = 6, memory_data = 0x33333333, read_value_1 = 0x11111111, read_value_2 = 0x22222222, read_value_3 = 0x33333333.

SUMMARY

SoC 03 완료 확인

  • Reset 해제 후 MicroBlaze V가 Reset Vector에서 Fetch를 시작한다는 것을 설명할 수 있다.
  • 기본 C_BASE_VECTORS가 0x00000000임을 확인했다.
  • ILMB는 Instruction, DLMB는 Data 접근 경로라는 것을 구분한다.
  • ILMB/DLMB가 Dual-Port BRAM으로 연결되는 실제 구조를 이해한다.
  • 16 KB가 0x4000 Byte임을 계산할 수 있다.
